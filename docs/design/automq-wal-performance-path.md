# WAL performance path and batching constraints

This analysis compares the current candidate with AutoMQ 1.3.4 at `bfb01a2ad27e04b1f057827a30bcfc465ee989aa`, using the locally retained source and diff described in [the comparison](automq-1.3.4-wal-comparison.md). It identifies work per request and dependencies, not measured throughput. The existing early `acks=1` experiment can acknowledge data before either WAL copy is durable.

## Critical path to an early ACK

AutoMQ's `ElasticLog.append` invokes the active segment, advances its logical end and registers an asynchronous flush callback. `BlockWALService.append0` adds a record to the current block under a short block lock and calls `tryWriteBlock`; it returns an append result without awaiting block write or flush. `tryWriteBlock` is rate-limited and dispatches a polled block to the I/O executor; a separate periodic scheduler retries polling, with a minimum 1 ms scheduling interval. That scheduler interval is not a wait before accepting each record. Independent block workers later complete their futures; the per-Stream completion sequencer and global trim frontier have separate roles.

Our eligible path calls `SharedUnifiedLog.appendAsLeaderTracked`, serializes the Kafka batches into owned buffers, submits a WAL group, and materializes Kafka metadata. `CoordinatedRingWalAdapter.submitBatch` now reserves ring space and a bounded writer slot for the active block before returning the reservation future. Additional groups fitting the same reserved extent can join it; growth is aligned and bounded by capacity and physical wrap. The assembler seals and submits blocks asynchronously. The ACK also waits for Kafka state publication and a leadership recheck, while the durable future still depends on data force and the global checkpoint. The assembler still uses the existing batching setting; no scheduling or rate-limit equivalence with AutoMQ is claimed. Actual contention and end-to-end costs remain unmeasured.

AutoMQ's `S3Stream.append0` associates each append with its own future and advances its stream confirmation after completion. Our partition tracker previously searched the entire pending deque for every confirmation query, including the common query for the exact end of the most recent reservation. It now checks that exact tail in constant time before falling back to the existing ordered search for interior offsets. Generation, failure, cancellation, contiguous confirmation and WAL/checkpoint requirements are unchanged; this does not independently confirm a later block or change replica visibility.

An isolated JVM diagnostic held 1, 4, 64, 1,024 and 4,096 uncompleted reservations and queried the same exact tail 20,000 times per size; the latter is the configured default admission limit, not an observed production queue depth. Two alternating baseline runs took about 76, 53–58, 266–363, 933–972 and 3,751–3,943 thread-CPU nanoseconds per query respectively; candidate runs took about 65–67, 30–31, 29, 9–11 and 12–13 nanoseconds. The small values and changing JIT state make these a rough complexity diagnostic only. The probe `/private/tmp/kafka-tail-confirm-probe/TailLookupProbe.java` does not measure WAL force, Broker requests, RF1/RF2 throughput or AutoMQ.

For a closed-loop producer with `N` outstanding requests and average request latency `L`, Little's law bounds steady throughput near `N / L` requests per second, before accounting for other constraints. Before the active-block change, a single queued group below the limits waited for the assembler's batching interval before physical reservation and early ACK. Now the reservation is made during admission, so that wait is no longer on the successful early-ACK path. One request can contain many Kafka records; scheduling delay, concurrent partitions, client batching, request pipelining and the number of producers change the result. The existing linger setting is not changed here.

## Physical work and batching

For a block with `G` atomic groups, one Kafka batch payload of `P` bytes per group, 4,096-byte alignment, a 64-byte block header, a 60-byte DATA header and a 60-byte group marker, the written block length is `4096 * ceil((64 + G * (P + 120)) / 4096)`, excluding wrap padding and metadata writes. For illustration only, if `P = 1024`, one group consumes a 4,096-byte block; three groups also fit in 4,096 bytes. Their data-write bytes per payload byte are respectively 4.0 and 1.33 before checkpoint writes. Kafka batch size is not necessarily the application message size.

The parallel writer has four workers and at most 128 pending blocks in the current adapter. It can coalesce completed writes into one data force. The current banked checkpoint separately writes three metadata slots and performs one force per advancing tail cohort; legacy metadata takes two forces. A later physically forced block still waits for every earlier block before its checkpoint and ordered durable result. Early ACK does not wait for these forces, but replica visibility, confirmed cache admission, eventual ring reuse and sustainable throughput depend on them. Force counts can be amortized across blocks and groups, so neither two forces per message nor a fixed throughput ceiling follows from the code.

RF2 adds a follower WAL path and replica transfer. Its resource demand includes two independent copies and network traffic, while `acks=1` does not wait for the follower. These stages can overlap on separate machines, so their latencies must not simply be added to early-ACK latency. On the same device or CPU they can contend. A guarantee that an acknowledged record survives loss of the leader and its WAL requires waiting for independent durable storage, which is a different ACK boundary.

## Priorities

1. **Admission before sealing.** The experimental parallel-block adapter now reserves bounded physical space and a writer slot while accepting groups into a single active block, and seals it asynchronously. Expansion is aligned, cannot cross the physical end, and cannot overlap another reservation; a full block is sealed before another is reserved. Same-extent appends avoid re-entering the allocator but still check failure fencing. This removes the assembler wait from the reservation dependency while preserving an opportunity to batch; it does not remove later durability forces. Real-Broker throughput, queue saturation, shutdown under sustained pressure and leadership cancellation still require validation before claiming the change is safe or faster end to end.
2. **Independent partition confirmation.** Complete a recoverable versioned window and authoritative replica/epoch reconciliation before using block-force completion as independent durable confirmation. Keep physical trim dependent on the contiguous, remotely covered and reader-drained prefix. The current window code is internal and Broker opening rejects it; it does not yet change runtime confirmation or throughput.
3. **Reuse owned batches.** Transfer an exact-sized, immutable owned payload into the bounded confirmed cache for both Fetch and upload. A slice of a larger allocation or a block decoded from disk must be copied, otherwise cache accounting omits retained memory. Cache publication stays after durability and index publication; invalidation and backend failure fencing remain required. This removes one payload-sized copy and allocation for eligible cached batches, not the serialization into the owned buffer or the copy into the encoded WAL block.
4. **Measure the actual pipeline.** Existing `WalBlockCount`, `WalBlockGroupCount`, `WalBlockRecordBytes`, early-ACK and cache counters can show path use and average groups per completed block. `WalDurabilityBatchCount` counts checkpoint cohorts, not physical blocks. In the parallel-block coordinator the exposed force/barrier time fields are currently zero placeholders; zero must not be interpreted as zero I/O latency. To decide whether admission, coalescing, CPU copies, force latency, follower replication or consumer reads dominate, add accurate bounded measurements at their actual boundaries and retain test/JAR/setting provenance. Do not infer p99 from averages or maxima.

Existing AutoMQ results remain historical reference data. Any claim that this candidate is close to or faster than AutoMQ requires its own comparable candidate measurements and a clearly labeled effective replica count, acknowledgement boundary and storage mode; no additional AutoMQ run is required to establish the above source-level facts.

## Single-batch Fetch reuse

AutoMQ 1.3.4's `S3Storage.read` returns matching batches from `deltaWALCache`, and `LogCache.StreamCache.get` selects existing batch objects. Our confirmed local cache likewise owns bounded payloads, but `SharedLogSegment.materializeFetch` previously copied even one cached batch into another array. A single local cache hit can now supply an immutable view directly to `MemoryRecords`; the returned view keeps the exact-sized backing bytes alive if the entry is evicted or the cache closes. This deliberately applies only when the selected record is the actual cache entry: a freshly decoded WAL block, remote result, or multiple selected batches still uses the existing contiguous copy. This avoids one payload-sized allocation and copy in that case, without claiming the full multi-batch behavior or reference-counting scheme of AutoMQ. In-flight Fetch responses may retain their backing arrays after cache eviction, as they previously retained their own response buffers. No throughput improvement is claimed without measurement.

AutoMQ's `LogCache.StreamCache.get` also locates the requested starting offset before walking selected batches. Our Fetch used to materialize every later local and remote index entry before applying its byte limit. It now locates the containing or next range in each ordered index and lazily merges them until the limit, retaining local precedence for equal starts and the existing post-read checks. Both indexes are concurrent and their iterators are weakly consistent, as with the previous iteration used to construct a list; this is not a cross-index transactional snapshot.

The selection retains the exact local WAL location, not just logical offsets. A changed location fails the read instead of silently substituting another same-sized batch. If the selected source is remote, the reader uses the remote range rather than a different overlapping local range; a remote read or local-to-remote fallback checks the complete selected offset range, epoch and byte length before issuing object I/O. Equivalent committed physical-object fallback and checksum validation still apply. These checks do not resolve conflicting remote metadata after a Kafka truncation or make offset coverage alone sufficient for WAL reclamation.

The built-in remote-coverage reclaim path now decodes records as temporary views of the freshly read block, rather than allocating another body buffer for every record. Both block and per-record checksums, complete-group framing and remote identity checks still run. The views are confined to that built-in policy; regular Fetch, replay and arbitrary caller-supplied reclaim policies retain independently owned record bodies, so they cannot keep a large block alive or observe later reuse. This targets an allocation site visible in a November 22 JFR from an older candidate, not a measurement of the present Broker.

A local in-memory diagnostic decoded a writable block containing 128 records of 1 KiB each and applied the real remote-coverage policy to every record. After warmup, later alternating samples allocated about 299,800 bytes per block with copied bodies and 156,300 with borrowed bodies; later average times were about 51 and 46 microseconds respectively, while an earlier borrowed sample took 60 microseconds. The `/private/tmp/ReclaimDecodeProbe.java` diagnostic excludes disk reads, checkpoints and Broker concurrency. It supports a reduced-allocation claim for this path only; it does not establish end-to-end throughput or exclude a regression under load.

The built-in remote policy now also calculates the payload CRC directly from the validated, pinned block slice. This avoids the JDK's temporary array for CRC32C on a read-only heap buffer. The slice is bounded using the decoded record's WAL address and length, stays inside the reclaim operation, and must match the decoded DATA payload length; external policies still receive independent records. In a follow-up run of the same in-memory workload, later samples allocated approximately 156,300 bytes per block for the previous read-only CRC path and 23,200 for the block-slice path; their later averages were about 47 and 39 microseconds, with an earlier slice sample at 56 microseconds. This is a focused JVM observation, not a Broker or AutoMQ comparison.

## Block record encoding

AutoMQ's block assembly holds record headers and bodies in a composite buffer, and its record generator can reuse a supplied body CRC. Our independent block format continues to use an owned contiguous block, but now writes each record directly into that block and computes its record CRC over the bytes already there. This avoids creating a separate record header and the JDK's temporary array for CRC32C on each read-only heap payload. The on-disk header, record CRC, group marker, locations, padding and block CRC are unchanged; the rotating and ordinary ring WALs retain their existing encoder. Tests compare the new record bytes to the prior record encoder for sliced heap and direct buffers, check an existing pre-change whole-block SHA-256, and exercise WAL replay and Broker behavior.

An in-memory `/private/tmp/BlockEncodeProbe.java` reconstructed the previous block encoder and verified byte-for-byte equality before timing, using one group of 1 KiB records and six alternating warmed samples. For one record, allocations were roughly 7.1 KB before and 4.7–5.2 KB after; time samples varied from about 1.2–1.7 to 0.6–1.7 microseconds. For four records, allocations were about 16.2 KB versus 9.4 KB, and later samples were about 1.8 versus 1.4 microseconds. For 128 records, allocations were about 361.5 KB versus 162.3 KB, and later samples were about 44.6 versus 32.3 microseconds. The old reconstruction does not allocate the final result wrapper, slightly favoring it; this local diagnostic excludes Broker scheduling, disk I/O, force, replication and object upload. It does not establish end-to-end throughput or rule out a regression in the user's workload.

## Checkpoint serialization

### Handling an unadmitted capacity rejection

The tracked append path now rolls back only its most recent, still-unsettled reservation when the WAL reservation future has already failed with `WalCapacityExceededException` before Kafka state publication.
