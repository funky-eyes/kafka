# AutoMQ 1.3.4 comparison and replicated-WAL design direction

## Scope and evidence

AutoMQ 1.3.4 is pinned to `bfb01a2ad27e04b1f057827a30bcfc465ee989aa`. Its actual Apache Kafka merge parent is `cc53a632edcf78dc8b2a4c2c502c654950744e1e` (Kafka 3.9.0); the official Kafka 3.9.0 tag resolves to `84caaa6e9da06435411510a81fa321d4f99c351f`. Those two Apache trees differ in three Controller/test files. Applying either complete comparison patch to its corresponding baseline reproduced AutoMQ tree `fbd2096779c9e88d06364e65abf1da22d6f5cd23`.

The locally retained [full source comparison](../../build/wal-recovery-1122/upstream-diff/AUTOMQ-KAFKA-SOURCE-DIFF.md), full patches, and the Produce/WAL/Fetch/recovery focused patch are under `build/wal-recovery-1122/upstream-diff/`. That directory is ignored build evidence, not part of the Git commit. This document records conclusions and proposed work; it does not assert that the proposed design is implemented.

## The replica model is different

When the Elastic Stream switch is enabled, AutoMQ's Controller forces the Broker-level Topic replication factor and `min.insync.replicas` to 1, even if the create request specifies another factor. Its code says that storage replication is decided by Elastic Stream; the examined `ElasticLog` creates streams with a replica count of 1. The Elastic Partition code also replaces the previously calculated Kafka ISR-based high watermark with the Stream confirmation offset. These observations apply to the pinned version and examined path; they do not prove a separate replicated WAL is active in the measured deployment. See [Controller topic creation](https://github.com/AutoMQ/automq/blob/bfb01a2ad27e04b1f057827a30bcfc465ee989aa/metadata/src/main/java/org/apache/kafka/controller/ReplicationControlManager.java#L717-L732), [stream creation](https://github.com/AutoMQ/automq/blob/bfb01a2ad27e04b1f057827a30bcfc465ee989aa/core/src/main/scala/kafka/log/streamaspect/ElasticLog.scala#L638-L651), and [high-watermark calculation](https://github.com/AutoMQ/automq/blob/bfb01a2ad27e04b1f057827a30bcfc465ee989aa/core/src/main/scala/kafka/cluster/Partition.scala#L1280-L1308).

Our goal is an AutoMQ-inspired data plane with an independent WAL replica in another failure domain, so recovery does not depend on the lost leader's local WAL. The existing Kafka RF2 route gives each Broker its own WAL, but `acks=1` does not mean that the follower has already received or persisted the record. A Topic's requested RF, metadata assignment, in-sync replicas, per-broker WAL writes, and survival after loss of a specific broker must be checked separately. A request for RF2 against AutoMQ is not evidence of two Broker WAL copies. Do not copy its single-replica high-watermark override into our RF2 path.

There are two distinct contracts. In the authorized default-off early-ACK experiment, a record may be acknowledged before any replica has persisted it and can be lost if its leader fails. To guarantee recovery of an acknowledged record after permanent leader/WAL loss, a separate explicitly configured stronger mode must wait for an independently durable replica or equivalent recoverable storage before responding, even if the client requested `acks=1`. That strengthening changes standard Kafka `acks=1` availability and latency and must not silently become the default. RF1 cannot supply an independent local WAL replica on its own.

## Differences along the data path

| Area | Pinned AutoMQ behavior | Our candidate and consequence |
| --- | --- | --- |
| Append and ACK | Elastic append updates its logical log end, submits asynchronous Stream work, and advances `confirmOffset` after completion. The normal Produce logic delays successful responses for `acks=all`, not `acks=1`. | The default experimental async path waits for ordered durable confirmation. The separate default-off early-ACK switch allows eligible RF1/RF2 requests to return after physical ring-space reservation. Both fast paths currently require a single partition and non-idempotent, non-transactional records; other requests retain the synchronous path. |
| Partition confirmation | WAL block completion and Stream-ordered callbacks are distinct; each Stream sequences its own completions before confirming and caching records. | `PartitionDurableOffsetTracker` maintains per-partition order, but its underlying WAL future is held behind the broker-wide contiguous persisted tail. A preceding block can delay unrelated partitions. |
| Block I/O and recovery | Blocks are assembled under a short lock and written by parallel workers. An in-memory window tracks the earliest unfinished position; normal block completion does not persist a new global tail header. Recovery scans using the persisted header, window, offsets and record validation. | `RingBlockCommitCoordinator`, `BlockRingCheckpoint` and `BlockRingRecovery` use a durable contiguous `[head, tail)` checkpoint and fail closed on corrupt committed data. Removing tail forces without changing recovery would weaken the current contract. |
| Cache and upload | After Stream-ordered WAL confirmation, the record is retained in a capacity-limited Delta WAL cache used by hot reads and upload. Upload commit advances trim; cache ownership then transfers or is released. | The rotating-file WAL already has its own bounded cache populated after durable append; the parallel-block WAL uses a bounded engine cache shared by Fetch and upload. For owned batch groups the engine now copies the batch into that cache after WAL confirmation and successful index publication; other entries fill on their first validated WAL read. Cache hits still take `walMaintenanceLock`, and reclaim still reads blocks. The cache checks backend failure fences on hits, accounts for entry overhead, and discards entries on reclaim or close. Its independent lock prevents append completion from waiting on the maintenance lock. |
| I/O semantics | The examined direct-channel implementation can use `O_DIRECT`; its direct-channel flush is empty. The file-channel fallback performs a force. | Our NIO and Java AIO backends use explicit force. Java AIO submission alone does not make force asynchronous or equivalent to AutoMQ's direct I/O. Filesystem and device durability must be recorded. |

Source entry points: [Elastic append](https://github.com/AutoMQ/automq/blob/bfb01a2ad27e04b1f057827a30bcfc465ee989aa/core/src/main/scala/kafka/log/streamaspect/ElasticLog.scala#L181-L242), [block scheduling and completion](https://github.com/AutoMQ/automq/blob/bfb01a2ad27e04b1f057827a30bcfc465ee989aa/s3stream/src/main/java/com/automq/stream/s3/wal/impl/block/SlidingWindowService.java#L515-L545), [per-Stream completion and cache](https://github.com/AutoMQ/automq/blob/bfb01a2ad27e04b1f057827a30bcfc465ee989aa/s3stream/src/main/java/com/automq/stream/s3/S3Storage.java#L675-L705), and [commit and trim](https://github.com/AutoMQ/automq/blob/bfb01a2ad27e04b1f057827a30bcfc465ee989aa/s3stream/src/main/java/com/automq/stream/s3/S3Storage.java#L825-L839). Our corresponding code is in `SharedUnifiedLog`, `PartitionDurableOffsetTracker`, `CoordinatedRingWalAdapter`, `RingBlockCommitCoordinator`, and `SharedStorageEngine`.

### Detailed completion and recovery boundaries

1. `ElasticLog.append` reserves a byte permit, appends to the active segment, advances the logical log end and registers a flush callback; it does not wait for that callback before returning. The callback advances the log's confirmed offset and queues a notification to a shared executor. This is separate from `S3Stream.append`, whose own future advances the Stream's confirmation only after `S3Storage` reports completion. Thus an early Produce response and a confirmed Stream record are different events. See [ElasticLog](https://github.com/AutoMQ/automq/blob/bfb01a2ad27e04b1f057827a30bcfc465ee989aa/core/src/main/scala/kafka/log/streamaspect/ElasticLog.scala#L181-L242) and [S3Stream](https://github.com/AutoMQ/automq/blob/bfb01a2ad27e04b1f057827a30bcfc465ee989aa/s3stream/src/main/java/com/automq/stream/s3/S3Stream.java#L181-L205).
2. A block worker writes and flushes its own block, then marks it complete in the in-memory window and completes that block's futures. `WALCallbackSequencer` releases only the contiguous completed requests for the same Stream; a gap in a different Stream does not hold this Stream's callback. A separate `WALConfirmOffsetCalculator` periodically derives the global contiguous position used to constrain cache archival and trim. See [block write](https://github.com/AutoMQ/automq/blob/bfb01a2ad27e04b1f057827a30bcfc465ee989aa/s3stream/src/main/java/com/automq/stream/s3/wal/impl/block/SlidingWindowService.java#L419-L426), [Stream sequencing](https://github.com/AutoMQ/automq/blob/bfb01a2ad27e04b1f057827a30bcfc465ee989aa/s3stream/src/main/java/com/automq/stream/s3/S3Storage.java#L1009-L1075), and [global calculation](https://github.com/AutoMQ/automq/blob/bfb01a2ad27e04b1f057827a30bcfc465ee989aa/s3stream/src/main/java/com/automq/stream/s3/S3Storage.java#L862-L940).
3. A full ring or cache causes AutoMQ to queue the request and attempt upload/backoff instead of treating capacity exhaustion as a completed append. Our current experimental path can materialize Kafka offsets before its asynchronous physical reservation fails; it fences the affected log directory on that failure. Replacing this with backpressure requires cancellation and draining on leadership change and shutdown, so that a full ring cannot deadlock Kafka state transitions. See [append backoff](https://github.com/AutoMQ/automq/blob/bfb01a2ad27e04b1f057827a30bcfc465ee989aa/s3stream/src/main/java/com/automq/stream/s3/S3Storage.java#L446-L519).
4. AutoMQ persists a window bound and scans within it during recovery, skipping invalid positions according to its record framing; it then reconciles recovered records against each open Stream's authoritative end offset, reorders when possible, and discards records after that Stream's first gap. See [WAL recovery](https://github.com/AutoMQ/automq/blob/bfb01a2ad27e04b1f057827a30bcfc465ee989aa/s3stream/src/main/java/com/automq/stream/s3/wal/impl/block/BlockWALService.java#L473-L485) and [Stream continuity](https://github.com/AutoMQ/automq/blob/bfb01a2ad27e04b1f057827a30bcfc465ee989aa/s3stream/src/main/java/com/automq/stream/s3/S3Storage.java#L168-L225). Our `BlockRingRecovery.scan` instead validates only the checkpointed `[head, tail)` and requires contiguous global group IDs; `SharedStorageEngine` replays this local prefix before authoritative remote metadata is available.

For our replicated design, the proposed replacement therefore needs a versioned recoverable scan window, validation of block generation/checksums and atomic groups, and a second phase that reconciles each partition against authoritative remote coverage, Kafka offsets and leader epochs before publishing it. It must preserve an independently durable follower's data during election, rather than adopting AutoMQ's single-Stream high-watermark override. The window's durable publication must precede any block acknowledgement that relies on scanning it; trim still requires committed object coverage and reader drainage. This is a design direction, not a completed protocol.

The experimental Broker completion path now batches notifications in partition-hashed scheduler lanes and retains any high-watermark-increased signal when merging checks for a partition. Each batch is limited to 1,024 notifications; this bounds a single drain, not the total pending queue. Scheduler saturation and total queued memory still need an explicit backpressure policy. This optimization does not change the underlying globally checkpointed WAL confirmation boundary.

## Implementation direction

1. **Separate acceptance, durable confirmation and Kafka visibility.** Add a default-off experimental early-ACK mode, explicitly authorized to lose ACKed data that has not reached the local WAL. Validate, assign offsets and publish the accepted append before responding, while tracking its independent durability future. Keep default durable ACK unchanged. Fence the original leader epoch before sending a response; a later write/force failure must fence the partition and prevent speculative log state, producer state or a clean-close marker from surviving as confirmed. Bound outstanding bytes and groups. Do not implement early ACK by merely completing the existing durability future early: other consumers rely on its durability contract.
2. **Make independent replica durability a first-class design.** Define whether Kafka follower replication or a separate WAL-replication protocol supplies the independent copy, and prove its actual durable progress, ownership/epoch fencing, failover and recovery before making a leader-loss guarantee. An opt-in stronger `acks=1` mode must wait for that proof without changing the durability contract of `SharedWal` futures. The current experimental Kafka-follower path bounds `LOG_END` reads at the confirmed frontier instead of HW, and an RF2 cross-node test covers one failover after replica confirmation. Compute HW from the confirmed leader position and eligible ISR positions under Kafka's rules. Drain or fence in-flight work across leader changes, ISR changes, truncation, shutdown, and RF1-to-RF2 changes. Preserve synchronous fallback for transactions, idempotence, multi-partition requests and unsupported conditions until each is explicitly designed and tested.
3. **Decouple block completion from the global reclaim frontier.** Design a new versioned WAL format and recovery protocol that can distinguish current-cycle records, atomic groups, torn writes, stale reused blocks and holes. A completed block must not be called recoverably durable until the new recovery contract can locate and validate it after a crash. Sequence completion per partition, keep an independent contiguous global position for safe reuse, and constrain trim to durably committed remote coverage plus drained readers. Prove migration and fallback before replacing the existing forced-tail format.
4. **Reuse the confirmed batch end to end.** The initial implementation copies owned data into the shared Fetch/upload cache after confirmation. Explore transferring exactly bounded immutable buffers without that additional copy, and reducing maintenance-lock contention; preserve eviction, in-flight references, memory accounting, backpressure, truncation and reclaim invalidation. Checked WAL reads remain the miss and recovery path.
5. **Measure and tune the complete pipeline.** Capture actual cache hits/misses, block occupancy, groups per block, I/O depth, force and checkpoint counts/time, queueing, allocation, upload and replica lag. Evaluate batching and direct I/O independently with filesystem/device semantics recorded. A microbenchmark or an option being configured is not proof that the broker exercised the intended path.

## Deferred negative reclaim checks

The parallel-block WAL retains at most one metadata-only hint for a block whose DATA range was not covered by remote metadata. Repeated reclaim calls can recheck that range against the current remote index without rereading the block while it remains uncovered. This hint only defers reclaim: when coverage becomes sufficient the whole block is read and validated again, all records are evaluated, and reader drainage and the forced head checkpoint remain mandatory. Other reclaim policies always receive freshly decoded records. A disk error in an uncovered block may therefore be detected later, when it is read or becomes eligible for reclamation. This reduces redundant reads in that specific case; it is not an end-to-end throughput measurement.

## Batched local block reads

The parallel-block WAL groups a batch of requested locations by committed physical block, reads and validates each requested block once, and checks every requested logical address and location against the decoded record. It pins one block at a time and fails if a later block was reclaimed before it can be pinned. Fetch selects local batches together before remote fallback, so cold Fetch and upload can use this grouped read; successfully validated payloads continue to populate the bounded local cache. Mixed local and remote batches preserve offset order. These changes avoid repeated block reads and decode on cache misses; they do not establish end-to-end throughput improvement or change WAL confirmation semantics.
